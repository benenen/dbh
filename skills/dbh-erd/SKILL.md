# 用 dbh erd 维护关系模型

`dbh erd`（简写 `er`）在项目根目录的 `.dbh/` 中维护 DBML 关系模型。Agent 通过终端直接运行本机 `dbh` 并读取实际输出。

## 写数据库代码前

1. 在编辑前查询本次涉及的表。从项目根执行；子项目有自己的模型时用 `--dir` 指定其 `.dbh/`。按当前需要选一条命令，涉及其他表时再补查。

   - 查字段、注释、索引和键：`dbh erd show TABLE --depth 0`
   - 查单表关系：`dbh erd relations --table TABLE --format tsv`
   - 查跨表 JOIN 路径：`dbh erd path FROM TO --format tsv`（存在多条平行/条件关系时加 `--all`）
   - 表名未知：`dbh erd tables --match KEYWORD --format tsv`（全量可省略 `--match`；多模型排查来源加 `--with-model`）
   - 按字段名或字段注释找表、需要逐字段比对（如与建表 SQL、文档核对）：`dbh erd columns [TABLE...] --match KEYWORD --format tsv`，每行一个字段，含类型、`pk`、`not_null`、`unique`、默认值和注释

   查询都走 `dbh erd`，不要用 `rg`、`sed` 或脚本直接读 `.dbml`：命令输出合并后的模型、`evidence` 列和上述 warning，直接读文件会漏掉这些信息。

   - stderr 出现 `warning: table T has different columns in models A, B` 时，输出是多个库的字段合并，按本次代码连接的库加 `--model` 重新查询。
   - stderr 出现 `warning: table T is only in another project's models ...` 时，该表来自同仓库其他服务的模型，可能不在本项目连接的库中；在本项目代码或配置中确认确实访问该库后再使用。

2. 按查询结果定位需要阅读的代码。对照迁移、模型定义或现有 SQL 核实本次依赖的字段和约束；推断关系的 JOIN 条件以业务代码为准。
3. 工具不可用、缺少模型或查询失败时，从迁移、模型定义或现有 SQL 获取缺失的信息，再继续写代码。此流程只查询本地文件；按用户要求另行拉取或生成模型。

## 子命令

### `init [NAME] [--db DB] [--model M]`

根据当前代码和数据库，在当前 `.dbh/` 中初始化生成数据库关系文件（`<model>.dbml` 与 `<model>.refs.dbml`）：

1. **确定位置**：若当前目录希望独立存放模型（而不是落到外层 Git 根目录），先确保当前目录存在 `.dbh/`；否则 `dbh erd pull --save` 会在 Git 根目录（无 Git 仓库则在当前目录）创建 `.dbh/`。
2. **确定连接与库**：未显式传入 `NAME` 时，运行 `dbh list` 并结合项目配置（如 `.env`、`config.*`、`docker-compose.*`，不输出密码或明文 DSN）匹配连接与库名；无法唯一确定时询问用户。用 `dbh check NAME --timeout 10s` 验证连通性。
3. **生成结构文件**：执行下节“生成或更新模型”第 2–3 步，生成 `.dbh/<model>.dbml`。
4. **提取代码关系**：执行下节第 4–6 步，扫描当前代码中的 ORM 关联、迁移脚本和业务 SQL `JOIN`，将确认的隐式关系连同源码位置注释写入 `.dbh/<model>.refs.dbml`。
5. **校验并汇报**：运行 `dbh erd check` 和 `dbh erd status`，修正所有 error 后按第 8 步汇报结果。

## 准备

- 先运行 `dbh erd --help`，核对当前版本支持的子命令和参数；没有 `erd` 子命令时，说明需要更新 dbh。
- `dbh list` 列出已保存的连接（凭据隐藏）。`NAME` 是连接名，`--db DB` 是服务器上的数据库名，两者不同；SQLite 由 DSN 指定文件，不支持 `--db`。
- 依据用户给出的目标选择连接；多个连接都符合且无法确定时，询问连接名或数据库名。没有合适的连接时，请用户用 `dbh new NAME --driver DRIVER --prompt-dsn` 自行保存，不要把 DSN 或密码写进命令历史、仓库或回复。
- 指定了配置目录时，所有命令带同样的 `--config-dir PATH`（或设置 `DBH_CONFIG_DIR`）。
- `dbh check NAME --timeout 10s` 验证配置、代理、认证和数据库访问，失败时退出码非零。
- 查询类子命令（`status`、`check`、`tables`、`relations`、`path`、`show`）默认从工程根目录（Git 仓库根目录，无 Git 则当前目录）递归扫描所有 `.dbh/` 并合并其中的关系模型；可用 `--dir PATH` 限定单个 `.dbh/`，用 `--model M` 限定单个模型名。除 `pull` 外的 `erd` 子命令只读 `.dbh/` 中的文件，不连接数据库。`pull --save` 仍只写入当前或向上最近的单个 `.dbh/`（可配合 `--dir` 指定）。

## 模型约定

- `.dbh/<model>.dbml`：数据库实际结构，由 `dbh erd pull NAME --save` 生成，可随时覆盖。不手工编辑支持 `pull` 的驱动的这个文件。
- `.dbh/<model>.refs.dbml`：从代码推断、数据库中没有外键约束的关系。只写 `Ref` 和注释，每条关系上方用 `// evidence: <源码位置>` 注释写明证据。`pull` 不会改动它。
- 默认模型名 `schema`；一个项目对应多个库时，每个库用 `--model` 取一个稳定的名字，所有命令带同样的 `--model`。

## 生成或更新模型

1. 按“准备”确定连接与数据库并 `dbh check NAME`；`dbh erd status` 查看已有模型。多个库或已有多个模型且目标不明确时，向用户确认模型名。
2. 拉取结构：`dbh erd pull NAME --save [--db DB] [--model M]`；PostgreSQL 支持 `--schema s1,s2` 读取多 schema，大库可用 `--include`/`--exclude` 过滤分表或加 `--timeout 5m`。覆盖已有模型时会自动输出 `Changes:` 变更摘要；也可先用 `dbh erd diff NAME --format tsv` 预览差异。支持 SQLite、PostgreSQL、MySQL 8.0.16+ / MariaDB 10.2.1+。
   - stderr 的 `warning: ... already declared` 表示该推断关系已成为数据库外键，从 `.refs.dbml` 删除对应 `Ref` 及其注释。
   - stderr 的 `error: ... unknown table/column` 表示推断关系已失效：在代码中重新确认，字段改名则更新，关系已不存在则删除。
3. MongoDB、Redis、ClickHouse 不支持 `pull`：根据 `dbh tables NAME --format tsv` / `dbh describe NAME TABLE --format tsv`（均支持 `--db`）手工整理 `<model>.dbml`，首行写 `// generated by: manual (<driver>)`，只写表和字段；这些库没有外键约束，所有关系都写进 `.refs.dbml`。
4. 在项目代码中查找数据库未声明的关系，证据按可信度排序：
   1. ORM 模型的关联定义，例如 GORM `foreignKey`/`references`、Django `ForeignKey`/`OneToOneField`、SQLAlchemy `ForeignKey`/`relationship`、TypeORM `@ManyToOne`/`@JoinColumn`、ActiveRecord `belongs_to`。
   2. 迁移脚本中曾经声明或计划声明的外键。
   3. 业务 SQL、查询构造器中的 `JOIN ... ON a.x = b.y`。
   4. 仅凭 `xxx_id` 命名推断。
5. 把第 1–3 类证据确认的关系追加到 `.refs.dbml`：

   ```dbml
   // evidence: app/models/order.go:42 (GORM foreignKey)
   Ref: orders.product_id > products.id
   ```

   每条证据单独一行 `// evidence: <文件:行号> (<证据类型>)`，同一关系可写多行；其他说明性注释不加前缀，不会进入 `evidence` 列。

   `>` 左侧是持有外键的表；一对一用 `-`，多对多用 `<>`；多列写成 `orders.(a, b) > t.(a, b)`。条件关联或多态关联（如 `a = 1` 时 `b` 关联 `c`，`a = 2` 时 `b` 关联 `d`）拆成多条 `Ref`，在紧邻 `Ref` 上方的注释块或行尾用 `// when: <条件>` 标注（如 `// when: a = 1`）。已在 `<model>.dbml` 中声明的关系不要重复写。
6. 第 4 类只凭命名的关系先列给用户，确认后才写入，注释写成 `// evidence: naming convention`。
7. 运行 `dbh erd check`，修正所有 error；再用 `dbh erd relations --source inferred --format tsv` 和 `dbh erd show` 核对。
8. 向用户汇报：模型文件路径、表数、declared 与 inferred 关系数、本次新增或删除的推断关系及证据、待确认的命名推断。不修改数据库结构；`.dbh/` 文件的提交按用户授权进行。

## 查询关系

回答“表之间怎么关联”“这条 JOIN 怎么写”时，先查模型，不必连接数据库：

```bash
dbh erd relations --table orders --format tsv
dbh erd path reviews users --format tsv
dbh erd show orders --depth 0
dbh erd columns orders --format tsv
```

- 查字段用 `show TABLE --depth 0`，查关系用 `relations --table`。只在需要看相邻表的字段时用 `--depth 1`：关联多的中心表一次可输出几十 KB；不带表名的 `show` 输出整个模型，只配合 `-o` 导出文件。
- `path` 每行一跳，`from_columns`/`to_columns` 即 JOIN 条件两侧的字段；`condition` 非空时在 JOIN `ON` 或 `WHERE` 中带上该条件；`source` 为 `inferred` 的一跳来自代码推断，数据库不保证引用完整性，使用前说明这一点；`evidence` 列给出推断依据的源码位置，需要核实 JOIN 条件时直接打开该位置。
- `--declared-only` 只走数据库外键。
- 没有 `.dbh/` 或模型时，按上一节先生成模型，或在用户同意后改用 `dbh describe` 等直接查看结构。
- 需要图形时用 `dbh erd show --format html -o erd.html`（或 `--format html --open` 直接在浏览器打开）导出可离线查看的交互式 HTML ER 图，或用 `--format mermaid` / `--format dot` 输出。
